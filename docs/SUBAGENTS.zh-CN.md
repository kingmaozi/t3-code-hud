# T3 Hub 角色分工与三级协作

Hub 把角色配置与协作方式分开：角色决定派给谁；协作方式是写入规则文件的提示，是否被当前会话读取取决于宿主。它不切换主会话模型，不改变权限审批，也不会自动计数或保证调用比例和费用。

| 等级 | 执行 Work | 审查 Review |
| --- | --- | --- |
| L1 | `worker`，默认 Muse Ember / max，处理边界清晰的工作 | `review-fast`，默认 Muse Ember / max，快速只读审查 |
| L2 | `worker-pro`，默认 Codex Sol / xhigh，处理更困难或升级的问题 | `code-review`，新配置默认 Codex Terra / max，模块级只读审查 |
| L3 | 主会话兜底，不创建第三个执行子代理 | `review-pro`，默认 Codex Sol / max，高风险只读终审 |

已有 `code-review` 配置会保留其实际模型、档位和提示词；例如原来是 Terra / high 就继续显示 high。新增审查档在未保存前是可路由的默认建议，并标记“默认未保存”；保存后才写入配置。模型、思考强度和提示词可逐个修改，项目覆盖优先于全局，项目未设置时继承全局。各级仍使用 T3 原生六类 `role`：`research`、`implementation`、`review`、`general`、`design`、`test`，等级不是新增的原生 role。

“T3 蜂群总指挥”是 Hub 的协作提示，不会调用 AGY 原生 `/swarm`。应用常规模式时，提示小任务、短任务由主会话直接完成，长任务按需分工；应用总指挥模式时，主会话默认负责决策、拆解、派单、协调和验收。对同一实现问题，提示主会话在 L1 连续两次未解决后转 L2，L2 连续两次未解决后亲自兜底；用户明确要求亲做也可例外。不要求无关角色重复尝试。这些次数由主会话判断，不是运行时强制执行的计数器。

开关写入已发现宿主规则文件的同一个 Hub 托管区，开关两种提示互斥；区块仅面向 T3 Code 顶层会话，独立宿主忽略。托管区外的用户规则不被覆盖，可能存在更高优先级或冲突规则。状态中的“已同步”仅表示文件回读匹配，不证明现有会话已经重新读取。可用时应让宿主重新加载规则或使用新会话；不要为此中断其他任务。

启用 Hub 的子代理路由 PreToolUse 守卫、且宿主实际支持该 Hook 时，守卫读取当前路由，在可识别的 `delegate_task` 请求中更新目标；若存在字符串 `task`，会在任务前加上该级提示词，并保持重复运行幂等。它只返回修改后的工具输入，不批准或绕过权限检查。无法识别任务字段时不会猜测写入；工具不可用时应如实说明，而不能把没有派单当成失败。子代理提示中要求不得递归派发通用子代理或启动宿主原生蜂群，生图、browser 等宿主内置专用能力除外；这是一条提示词约束，不是运行时权限隔离。

守卫只处理已核实的 T3 命名空间；其他同名工具和未核实的包装调用不会被改写。显式指定远程环境或项目的目标保持原样；跨模型时若原选项或 driver 无法确认兼容，也保留原请求并提示。任务与提示词合计超过 120000 字符时保留原任务并提示，不会截断。

派单时在 `title` 或 `clientRequestId` 中写明等级对应的角色 ID，例如 `review-fast · 检查变更`、`code-review · 模块审查`、`review-pro · 高风险终审`；三者的 T3 原生 `role` 都填 `review`。执行两档同理使用 `worker` 或 `worker-pro`，原生 `role` 填 `implementation`。没有明确等级时，`review` 默认使用 L2 `code-review`，`implementation` 默认使用 L1 `worker`；不会自动判断升级级别。
