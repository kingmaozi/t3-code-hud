# 实现试探、被否定的判断与接续注意事项

本文件保留会影响下一位实现者决策的试探过程，不能当作所有候选均已通过的证明。最新用户要求、当前安装状态和 Issue 优先级分别见 `REQUIREMENTS-AND-EXPERIMENTS.zh-CN.md`、`HANDOFF.md` 和 [总入口 #10](https://github.com/kingmaozi/t3-code-hud/issues/10)。本机证据在忽略目录 `.handoff-local/`，不得上传。

## 1. Hub 没出现：ASAR 推断被真实 Electron 证据推翻

最初用普通 Node 判断 `app.asar/package.json` 不存在，推断 bootstrap 门控必然失败，曾尝试只检查 `app.asar` 文件本身。随后独立审查在真实 T3 Electron、`ELECTRON_RUN_AS_NODE=1` 下验证：Electron 能读取归档内部路径，原门控可以成功。放宽门控会误选无效归档，因此该修改和错误的假 ASAR 测试已撤回。

实际确认的另一问题是安装脚本对已有 `t3-hud` 符号链接直接 `cp`，会写穿旧 userdata 副本。改为先移除链接本身，再安装规范入口。

启动链还曾在 spawn 后提前写 marker、仅看到 inspector 地址就算成功；已改为注入表达式真正成功、RPC 与进程一致、目标窗口实际 mounted 才认定就绪。仅 PID 存活、RPC 文件存在、`lastInjectError=null` 初始值都不足以证明挂载。

独立审查进一步发现共享 marker/RPC 在并发失败启动时可能覆盖或清掉正常实例，改为校验归属并采用 per-PID RPC。旧 RPC 可用于显式 reload 的兼容入口，但缺少 `mounted:true` 时不能假称新版已就绪。

没有采用未验证的 SIGUSR1 热注入，也没有设置全局 `launchctl NODE_OPTIONS`。历史授权过一次恢复重启；后续明确要求保护任务、不再重启，已用现成 reload。接续者不得把历史的一次重启授权当作新的重启授权。

## 2. Python / ACP：收尾崩溃与请求重放必须分开处理

诊断报告指向 Xcode Python 3.9.6 的解释器收尾与守护线程缓冲 I/O 锁，出现 `Py_FinalizeEx` / `SIGABRT`，并非证据显示 ACP `.par` 本体崩溃。采用 Homebrew 解释器、原始 fd 转发及受控退出，保留子进程非零退出码；文件更新不会改变已经运行的旧解释器。

多轮审查曾抓出以下真实边界，不能在重构时重新引入：

- 取消看门狗只退出 wrapper 会遗留孤儿；需终止并回收子进程。
- 安装器不能在固定 shebang 缺失或不可执行时覆盖有效安装；新版本只有合法 `.par` 时也应识别，检查模式不能产生写入。
- 不能按创建前后目录差异删除零字节数据库；并发其他请求可能拥有该文件。改为只计数，不删用户数据库。
- 退避期间收到副作用仍重放请求有重复执行风险。后续更严格地去除了 setup 请求自动重放；不要恢复早期“重试更健壮”的方案。
- stderr 原文可能包含 token、API key 或 JSON 凭据，普通日志不能保存原文。
- 正常退出需要排空输出；迟到取消必须切换有界退出，不能永远卡在慢读客户端。
- 等待重试/转发线程的时序不能丢最终响应。早期有针对该竞态的修复，但当前“不增加请求/不自动重放”的要求优先。

历史 `HTTP/1.0 502 Bad Gateway` 只能确认是真实失败，没有足够保留的上游证据确定根因。成功的隔离调用不能证明历史 502 永久根治。用户随后禁止额外 AGY 请求、登录与认证探测，不能为复现而绕过这个边界，也不能承诺第三方使用不会封号。

## 3. 计划来源与悬浮布局的多次修正

最初计划板附着在原生详情卡片下面；详情容器会随内容收缩，把它的底边当窗口底边曾导致只剩约一行高度。后来按可视窗口计算空间、默认向下展开、正文内部滚动。用户随后进一步要求任意拖动，改成独立悬浮仪表盘，保留位置、收起/展开与复位，不能侵入 React 管理的原生 DOM。

原生路由首段曾被误记为项目 UUID，后从真实安装包确认是 `environmentId/threadId`。必须校验运行环境，再从 thread 与 project 关联确认工作目录；draftId 不是项目身份，未知归属不可借用别的会话或项目。

计划来源补入真实原生 Plan、Markdown 计划和 AGY Brain 的 `task.md` / `implementation_plan.md`。同会话多个来源要按有效性和时效选择，不能读到错误会话或非普通文件。结构化步骤显示 N/M 和勾选；仅有文档则显示原文及“进度未量化”。

曾在无主计划时把子任务状态放进悬浮窗。用户最终纠正：**子代理仅在完整任务面板，悬浮窗标题统一“任务面板”，删除底部子代理/Hooks/插件快捷栏**。不得用旧需求恢复这些内容。

最新未安装 UI 候选还修正：焦点保护时快照签名提前消费导致失焦不刷新；RPC 错误重绘打断编辑；旧 DOM 下标指向新 cache 导致点 A 操作 C；HTML 属性将 CRLF/CR 归一导致合法步骤不能勾选。步骤和产物须使用项目/会话及稳定身份匹配，歧义时拒绝，不能猜下标。

最新卡片点击需要 Finder 定位所在文件夹并选中文件，完整任务页仍可 Markdown 预览。复用已有后端 reveal 路径及 realpath/会话归属保护，避免把 `.app` 等产物作为程序启动。新候选的实现者测试不替代独立复核和真实 T3/Finder 验收。

## 4. 路由开关：“写到磁盘”曾被过度解读

早期有 Carbon/Argon Orchestrator 与独立 swarm 等重叠入口，已整理为统一协作方式。Work 两档执行加主会话兜底，Review 三档审查；仍使用 T3 原生 role，不发明额外原生通道，不保证固定调用比例或代码产出比例。

全局配置与托管规则保存增加过事务预检、CAS、回滚保护；不能在失败回滚时覆盖用户并发编辑。已存在的非托管 Claude agent 文件保留，不能为了“全同步”强行覆盖。

目前磁盘总指挥 ON、九角色及六处托管块匹配。用户明确说明**新开会话**仍不派单，并回答旧七角色/high，所以“旧会话没刷新”不是充分解释。实际 AGY profile 扫描的 skill 是独立旧拷贝，共享目录和另一个配置目录也有不同副本。

当前 guard 仅改写已经发生的 `delegate_task`，并不会触发它。T3 自身原生 orchestration 提示允许普通编码亲做；Hub 开关不是该注入条件的输入。没有用广泛禁止 Shell 的手段强迫派单，这会误伤正常协调与权限语义。

两个研究方向均未实现：

1. 把静态 skill 改为实时 Hub 路由的引用入口，并验证真实被扫描的副本；不能只修共享目录而漏掉 profile 副本。
2. 对支持的宿主研究每轮 additionalContext；必须证明顶层身份、当前轮关联和加载时机，不能泛化到其他宿主。

[AGY 官方 Hooks](https://antigravity.google/docs/hooks) 描述的 `injectSteps`，在本机 ACP SDK 的 `ExternalPreInvocationHook` 中明确被忽略。禁止把注册 Hook 当作已成功注入。[Codex UserPromptSubmit](https://learn.chatgpt.com/docs/hooks#userpromptsubmit) 是另一条提案；[公共输入字段](https://learn.chatgpt.com/docs/hooks#common-input-fields) 指出子代理的 session_id 可能是父 ID，因此不能仅据该字段开启总指挥。native thread/turn、lineage 以及投影落库时序尚待验证。

## 5. MCP、插件所有权和缓存路径

卡片化展示、原生 Agent 绑定与 Hub 转发是不同操作。原生 Context7 配置和 Hub 转发都开时可能重复，当前状态必须回读，不能将插件缓存目录存在当作启用。

审查曾发现插件别名让位给用户原生服务后仍留在 discovery，导致把用户服务置为关闭；还发现只检查首个同名定义会漏掉后续原生定义。修复按归一化名称检查全部冲突，并区分同名不同端点，不能静默合并独立服务。

损坏 registry/state、非对象作用域值必须在写入前拒绝；缺文件可以是初次安装，损坏文件不是空配置。插件全局→off 不能误用请求附带的当前项目根；项目 owner 缺失不能猜当前项目。现存项目 Hook 的跨范围迁移仍受旧数据模型限制，界面按只读处理。

stdio probe 缓存曾因 `/var` 与 `/private/var`、符号链接与 `../cwd` 复用到错误结果，统一使用规范项目根。已加载旧模块的长驻 MCP CLI 不随 Hub backend reload 自动换代码；不能说所有原生进程已热更新。

## 6. 速度、缓存与容量：不要用推测补满 UI

已有统计修复过 provider 切换、缺 usage 继承旧比例，以及用可重置 ordinal 选择“最新轮”的错误。整轮缓存与最后一次调用缓存是不同分母，不能看到百分比不等就当成 ACP 丢数据。

本次只读核对证实实际 T3 DOM 选择器匹配，不能把未取证的“选择器失配”当根因。活动速度依赖 running、末条 assistant 可见增量、约260ms采样和最小增量/时间门槛；后端只接受明确当前轮的完成样本。截图时没有完整 DOM 采样证据，速度为何一直等待仍待复现。

当前 ACP 活动 `usage_update` 是 used/size/可选 cost，不包含缓存 token；运行中不写 `turnTokenUsage`，终止后才汇总。因此缓存缺失时不能用字符、上轮或累计数制造实时率。可改等待状态文案，并在真正收到当前轮数据时刷新。

模型窗口、上下文占用和客户端压缩阈值不同；AGY App 与托管 ACP 版本号也不是一条版本序列。继续按运行时上报识别，不因社区“512K”改常量，也不把 T3 入口指到原生 AGY App。

## 7. 梦境：定时器、跨进程调用和模型执行是三件事

自动整理采用共享记忆库，不另建镜像库。新增或近似候选不足时跳过模型；核心、置顶、疑似秘密、被引用和无法保全历史的内容保留；归档不覆盖旧归档，无法证明工作树已消失时不删它。

调度增加 sidecar 单例租约和热 reload 生命周期保护。真实页面曾显示“定时器未运行”，但实际 sidecar 已运行：renderer 默认先走主进程 backend，读到了另一个进程未启动的 scheduler。已把 `memory:dream:*` 固定到鉴权 sidecar；响应未知不能回退到另一个进程重放。

已保存 Muse Ember / medium / 03:30 Asia/Singapore / enabled / wake catch-up；可执行文件存在只证明静态可用，不证明登录、模型权限或执行成功。

两次真实手动结果均已保留：第一次 1.311 秒、第二次 4.575 秒；本地成功、Agent `cli-exit-1`、0合并/0归档/0内容变更。两次快照总数之间新增的是其他工作记录，不是梦境整理产生。

第一阻点通过禁止全部网络的离线探针确定：Muse 不接受 `--prompt-file /dev/stdin`，要求普通文件。修为独立0700目录、0600文件，正文不进 argv，成功/错误/超时均按 inode 非递归清理；该修复已热装。强杀/断电仍可能留下权限受限文件，没有引入全局递归清理。

普通文件探针通过参数值校验并进入模型流，禁网后 transport 失败仅是离线探针的预期，不能解释第二次生产失败。原始 stderr 只有内存片段、持久报告被压成退出码，现有材料无法确定第二阻点。没有把网络、认证、额度或模型 ID 当成已证实原因，也没有用失败时估算 token=0 宣称免费。

下一方案是从有界内存输出中提取固定白名单类别/HTTP状态，未知为 unknown，禁止落盘原文、地址、秘密与提示词。目前只有18项先红测试，源码未实现；停止开发时原样交接。不得吞掉这些红测后声称分支全部通过，也不得连续盲目重试真实整理。

## 8. 本次停止点

用户要求先交接、换 T3 自己解决，随后强调保留全部需求和试探。已停止开发/测试和模型尝试，建立独立 worktree，保留未完成代码、红测、Issue及本机证据。新的接续会话先复核这些事实与当前环境，再按用户授权范围推进；不能继承旧日志中的成功结论当作最新候选已经上线。

## 9. T3 v0.1.10 切换聊天后 Hub 仍读到旧草稿

真实窗口证实：T3 在一个草稿地址被晋升成会话后，`location.hash` 可以保持旧 `/draft/<id>`，而 `window.__TSR_ROUTER__.state.location.pathname` 已更新为当前环境/会话路径。HUD 和 Hub 都优先看 hash，所以把已运行的会话误显示为“新会话”，Hub 上下文也会以草稿路径拒绝读取。修复候选调整为先读已解析的 TanStack 路由，缺失时才回退到 hash；路由落在 `/` 时归为新会话，避免拿旧 hash 或缓存上下文显示上一聊天。Hub 原有三秒路由检查及 HUD 轮询继续发现相同 hash 下的 router 路径变化。

本轮已加入跨聊天切换、Hub 上下文 RPC 与首页隔离回归。新增 HUD 轮询用例在基线源码失败、修复后通过。独立复核使用 `TMPDIR=/private/tmp` 执行 `hud-promoted-draft-route` 与 `hub-v3-frontend-contract-xss` 两套定向测试，444/444 通过；默认临时目录下的两项预览路径测试失败也在干净基线复现，规范路径下通过。

2026-11-17 已备份并仅热更新 renderer 基础文件与 Hub 抽屉，保留原 sidecar 连接，通过现有 UI 热重载入口注入。实际窗口验收确认：已有聊天恢复用量、Hub 显示已连接、任务面板解除连接错误；切换两条已有聊天时用量随之更新，首页和未发送消息的草稿不会沿用上一聊天的数据，返回原聊天后用量再次恢复。安装文件与审查候选哈希一致，T3 主进程及 sidecar 未重启，未发送模型测试消息。上述结论覆盖此次本机热更新与交互验收，不等同于长期稳定性或其他电脑已安装验证。
